# 案件字段的法律含义（研发理解参考）

## 一、案件的身份与基本属性

`doc_id` `案号` `法院` `审级` `案由` `程序` `裁判日期`

- **案号 / doc_id**：案号是法院给案件的编号，如 `(2021)沪0104民初28195号`。它在法律上唯一标识一个案件，但同一份文书在不同来源可能重复出现，所以 `doc_id` 在案号后又加了一段内容指纹去重。研发只需把 `doc_id` 当作主键用。

- **审级**：中国民事诉讼是“两审终审”。
  - **一审**：案件第一次审理。
  - **二审**：当事人不服一审、上诉后的审理，二审判决是终审、立即生效。
  - **再审**：对已经生效的判决，发现错误后启动的特殊纠错程序。
  这个字段对类案很重要：如果一篇是“二审改判”，意味着一审的结论被上级法院推翻了——引用这类案件要看清楚到底哪一审的说理才算数。我们库里 98% 是一审。

- **案由**：案件的纠纷类型，本库统一是“买卖合同纠纷”。它是法院对“这是什么官司”的法定分类。

- **程序**：法院用哪种程序审的，以及被告是否到庭。
  - **普通程序**（合议庭三人）/ **简易程序**（独任一名法官，案情简单）/ **小额诉讼**（标的额很小，一审终审）。
  - **缺席**：被告经合法传唤没到庭，法院依原告提供的证据径行判决。研发要注意：缺席案里被告没有答辩、没有质证，所以“争议焦点”往往是原告单方主张，没有经过双方对抗，质量上要打个问号。

- **裁判日期**：判决作出的日期。本库集中在 2022 年。

## 二、当事人：谁和谁在打官司

`当事人[]`（每项含 `角色`、`名称`、`类型`）

- **角色**：原告、被告、第三人，二审里叫上诉人、被上诉人。
- **名称**：当事人名字，可能已脱敏成 `×××`（个人信息保护，属正常现象，不是数据缺失）。
- **类型**：企业 / 自然人 / 个体工商户 / 其他。

## 三、这桩买卖在法律上是什么

`法律关系` `标的物类型`

- **法律关系**：这笔交易在法律上的定性。普通买卖、网络购物（适用电商和消费者规则）、分期付款买卖（涉及所有权保留、解除限制）、拍卖等。同样叫“买卖”，法律关系不同，适用的法律就不同。取值来自受控词表。
- **标的物类型**：买卖的东西是什么（服务器、钢材、食品……），自由文本。它本身不决定裁判规则，但能反映行业场景。

## 四、争议焦点：这个案子到底在争什么（最重要）

`争议焦点`，含四层：`焦点标签`、`焦点评析{案情核心, 法律争点, 裁判要旨}`、`焦点原文`、`是否显式`，外加一个置信度字段 `置信`

这是整个数据集的核心，研发务必理解。

**什么是争议焦点**：一个案件里，当事人真正有分歧、且法院必须裁断的核心法律问题。它不是“谁赢谁输”，而是“争的是哪一个点”。比如同样是欠货款，有的争“货到底交付了没有”，有的争“收了货为什么不及时提质量异议”，有的争“公司没钱了股东要不要还”——这些是不同的争议焦点。

四层从粗到细：

- **焦点标签**：粗粒度的争点分类（货款给付、质量异议、合同解除……），像贴标签，可多个。用于检索的粗筛，但太粗——几百个“货款给付”案内部其实千差万别。

- **焦点评析**：大模型提炼的厚版分析，是类案比对的真正信号，三段：
  - **案情核心**：事实层面发生了什么（谁向谁供什么货、钱怎么往来、争议怎么产生）。
  - **法律争点**：法院需要裁断的**具体法律问题**，要落到法律点上。比如“收货后未在合理期间书面提出异议，是否视为认可质量”，而不是泛泛的“质量有没有问题”。
  - **裁判要旨**：法院怎么说理、依据什么规则、得出什么结论。这一段是**裁判规则**，是判断两案是不是类案的核心。

- **焦点原文 / 是否显式**：很多判决书并不会明写“本案争议焦点为……”。只有约 13% 的案件法院明确写了（`是否显式=true`，`焦点原文` 摘录原话）；其余 87% 的争点是模型从说理里**推断**出来的（`是否显式=false`，`焦点原文` 为 null）。研发要清楚：大部分争点是推断的提炼，不是原文照抄。`焦点评析` 是“提炼”，`焦点原文` 是“逐字”，两者不同。

- **置信**：模型对本案争议焦点判断（主要是焦点标签）的把握程度，取值 0–1。值偏低说明模型自己也不太确定，研发可据此做过滤或挑出来人工复核。

## 五、裁判规则级的细争点：判类案的法律内核

`细争点`，含 `主叶子`、`细争点[]`、`裁判规则争点`

- **什么是裁判规则**：法院在本案确立的、能推广到同类案件的裁判道理（类似判例法里的 ratio）。比如“买方收货后未在合理期间书面异议，视为认可质量变更”就是一条裁判规则。
- 粗标签（货款给付）太宽，内部裁判规则各异。我们把它细分到**裁判规则级**的细争点谱系（53 个叶子，分七层：合同效力、履行事实、付款抗辩、解除救济、责任主体、金钱计算、特殊交易），判据是“**同一个叶子 ≈ 同一条裁判规则**”。
- **主叶子**：本案最具压倒分量的那一条裁判规则争点（一个案件可能涉及多条，主叶子是最关键的）。
- **为什么重要**：两个案件算不算“高度类案”，法律上看的就是裁判规则是否相同，也就是主叶子是否相同。这是类案判定的法律内核，研发理解类案匹配时应抓这个，而不是抓表面标签。

## 六、案件的结果

`裁判结果_标签` 以及金额字段 `诉请金额` `支持金额` `支持比例` `原审金额`

- **裁判结果_标签**：法院对原告诉请的处理。全部支持 / 部分支持 / 全部驳回 / 撤诉 / 调解 / 二审维持 / 二审改判 / 发回重审。这是“输赢”。
  - 重要观念：**类案判定看裁判规则，不看输赢**。两个案子一个判支持、一个判驳回，只要适用的是同一条裁判规则（只是事实证据不同导致结果不同），仍然可能是类案。输赢只用于“找对自己有利的判例”这种二次筛选。

- **金额字段**：诉请金额是原告主张的货款本金，支持金额是法院判付的本金，支持比例是两者之比。这里有几条法律口径上的映射，研发容易踩：
  - **全部驳回 → 支持金额 = 0、比例 = 0**。这是“法院判了、但 0% 支持”的信号，不是数据缺失。
  - **撤诉 / 调解 → 支持金额 = null**。这类没有公开的判付金额，是真的没有，不是 0。
  - **二审 → 一审二审金额口径不一致**，二审的诉请/支持/比例置 null，另用 `原审金额` 记原审判付的本金。
  - 一句话：**0 和 null 含义不同**——0 是判了不支持，null 是没有可比口径。

## 七、法律依据

`引用法条[]`（每项 `法律`、`条`、`款`、`原文`）

本案适用的法律条文，是裁判的法律依据。对类案的意义：两个案件引用同样的法条（尤其是民法典买卖合同章的同一条），是“法律适用同向”的硬证据，说明用的是同一套规则。

## 八、判决书的文本结构

`段落`，含 `诉称`、`查明事实`、`本院认为`、`裁判结果`

一份中国民事判决书有固定结构，这四段分别对应：

- **诉称**：原告说什么（诉讼请求 + 事实和理由）。
- **查明事实**：法院经举证质证后**认定**的事实（注意是法院认定的，不一定等于原告主张）。
- **本院认为**：法院的说理，是整篇最重要的部分——争议焦点、裁判规则都在这一段。我们的 `焦点评析`、`裁判要旨` 主要从这里提炼。
- **裁判结果**：判决主文（最终判了什么）。

某些段落可能为 null（判决书没写、或自动切分没切出来，尤其“查明事实”约四成切不出），属正常，研发取用时判空即可。

## 九、来源与抽取溯源

`来源` `_provenance`

- **来源**：这条记录的数据来源标注，如“裁判文书网CSV/买卖合同纠纷_去重”。
- **_provenance**：抽取溯源，含 `抽取模型`（如 `rule-layer + deepseek-v4-flash`）和 `抽取prompt_version`（如 `extract-v4`）。研发一般不直接取这两个字段做业务，它记录的是“这条记录是用哪个模型、哪版提示词抽出来的”，便于追溯和版本管理。
